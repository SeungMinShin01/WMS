# 브랜치 · 커밋 규칙

> PR을 쓰지 않는다. 팀장이 팀원 브랜치를 develop에 직접 병합하고 푸시한다.
> 커밋 형식과 빌드는 git hook과 CI가 자동으로 검사한다.
> md 파일 보는법 1. github 웹사이트에서 2. vscode에서 Ctrl + Shift + v

---

## 1. 브랜치

### 1.1 브랜치 목록

| 브랜치                | 담당          | 들어가는 것                                                             | develop에 병합             |
| --------------------- | ------------- | ----------------------------------------------------------------------- | -------------------------- |
| `main`                | 팀장          | 배포된 코드. 항상 동작하는 상태                                         | — (금요일, develop만 병합) |
| `develop`             | 팀장          | **유일한 통합 브랜치**                                                  | —                          |
| `feature/core`        | 팀장          | 뼈대: 테이블 DML, 엔티티(기준정보, 문서), Repository, enum, 패키지 구조 | —                          |
| `feature/document`    | 팀장          | 입출고 문서 등록 (입고·출고 공통 Service, 문서번호 채번)                | 스토리가 끝날 때마다       |
| `feature/inbound`     | 입고 담당     | 입고 목록·상세, 검수, 적재, 재고 조회                                   | 스토리가 끝날 때마다       |
| `feature/outbound`    | 출고 담당     | 출고 목록·상세, 할당, 피킹, 출고확정                                    | 스토리가 끝날 때마다       |
| `feature/master-data` | 기준정보 담당 | 품목, 거래처, 칸(로케이션) CRUD, 샘플 데이터                            | 스토리가 끝날 때마다       |
| `reference/wms-flow`  | 팀장          | 참고 구현 (팀원 스토리를 먼저 만들어 본 코드)                           | **병합하지 않음**          |

- 브랜치 이름은 **소문자와 하이픈만** 쓴다. (`InBound` ✕ → `inbound` ○)
- `master-data`는 기준정보(품목·거래처·칸)를 뜻하는 용어다.
- feature 브랜치는 **계속 같은 이름으로 쓴다.** 병합한 뒤에도 지우지 않는다.

### 1.3 규칙

| 규칙                                                  | 설명                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------- |
| **스토리 하나가 끝날 때마다** develop에 병합한다      | 여러 스토리를 모아서 한 번에 병합하지 않는다. 늦게 합칠수록 충돌이 커진다 |
| **매일 아침** develop을 내 브랜치에 합친다            | 다른 사람이 병합한 코드를 빨리 받아야 충돌이 작다                         |
| 매일 작업 끝내기전 내 브랜치를 **푸시**한다           | 개인 branch 푸시는 develop에 영향을 주지 않는다                           |
| develop 및 **main**에 **직접 커밋하지 않는다**        | develop에는 병합만 한다                                                   |
| 다른 사람 브랜치를 pull하지 않는다                    | 필요한 코드는 develop에 들어온 뒤 받는다                                  |
| `reference/wms-flow`는 병합하지 않는다                | 참고용. 여기서 브랜치를 따지도 않는다                                     |
| develop이 **CI 빨간불**이면 병합한 사람이 바로 고친다 | 고치기 전까지 다른 사람은 develop에 병합하지 않는다                       |

## 2. 매일 쓰는 명령어

### 2.1 처음 한 번

```bash
git config core.hooksPath .githooks   # 커밋 메시지 자동 검사 켜기 (한 번만)
git fetch origin                      # GitHub에 있는 브랜치 목록을 내 컴퓨터로 받아 오기

git switch develop                    # develop으로 이동 (없으면 GitHub 것을 받아 자동으로 만듦)
git pull                              # develop을 GitHub 최신 상태로 맞추기

git switch feature/inbound          # 내 담당 브랜치로 이동 (아래 표 참고)
git merge develop                     # develop에 들어온 뼈대 등을 내 브랜치로 받기
git push                              # 합친 결과를 GitHub의 내 브랜치에 올리기
```

| 담당     | 브랜치                |
| -------- | --------------------- |
| 입고     | `feature/inbound`     |
| 출고     | `feature/outbound`    |
| 기준정보 | `feature/master-data` |
| 팀장     | `feature/document`    |

> - `pull`은 브랜치를 바꾸지 않는다. **지금 있는 브랜치에** GitHub 내용을 합칠 뿐이다. 브랜치 이동은 항상 `switch`로 한다.
> - 명령 전에 `git branch`로 지금 어느 브랜치에 있는지(`*` 표시) 확인한다.
> - `git switch`가 안 되면(Git 2.23 미만) `git checkout 브랜치이름`으로 똑같이 된다.

checkout으로 브랜치를 오가는 대신, 내 브랜치에 계속 있으면서 pull로 받고 push로 올리는 방식으로 바꿨습니다.

### 2.2 작업 시작전

내 브랜치에 있는 상태에서 develop 최신을 받아 합친다. 브랜치를 옮기지 않는다.

```bash
git branch                           # 지금 내 브랜치(* feature/inbound)에 있는지 확인
git pull origin develop              # GitHub의 develop을 받아서 내 브랜치에 합치기
                                     # 충돌이 나면 여기서, 내 브랜치에서 해결
```

### 2.3 작업 중

```bash
1. 왼쪽 **Source Control** 아이콘을 누른다. (`Ctrl + Shift + G`)
2. 올릴 파일 옆의 **`+`** 를 눌러 **Staged Changes**로 옮긴다.
3. 위 메시지 칸에 커밋 메시지를 쓰고 **Commit**을 누른다.
4. **Sync Changes**(또는 `…` → Push)로 올린다.

> 2번 이후 터미널에서 해도 된다. (1,2 는 소스제어쪽이 직관적)
git commit -m "feat(inbound): 입고 문서 목록 조회 API (ED-13)"
git push                             # 내 브랜치를 GitHub에 올리기 (작업종료/평일 퇴실 전에는 반드시)
```

> IDE에서 커밋해도 **커밋 메시지 자동 검사(git hook)는 똑같이 동작한다.** 형식이 틀리면 IDE에 에러 창이 뜨고 커밋되지 않는다.

#### 체크하지 말아야 할 파일

| 파일                              | 이유                         |
| --------------------------------- | ---------------------------- |
| `.idea/`, `.vscode/`, `*.iml`     | 각자 IDE 설정. 사람마다 다름 |
| `application-local.yml`, `.env`   | 내 DB 비밀번호가 들어 있음   |
| `build/`, `out/`, `node_modules/` | 빌드 결과물                  |

이 파일들이 목록에 자꾸 보이면 `.gitignore`에 빠져 있는 것이다. 팀장에게 알린다.

### 2.4 스토리가 끝났을 때: develop에 올리기

```bash
# 1) develop 최신을 내 브랜치에 먼저 합친다
git pull origin develop              # 충돌이 나면 여기서 해결 (못하면 팀장한테 보고)

# 2) 내 브랜치도 GitHub에 올려 둔다 (브랜치는 지우지 않고 계속 쓴다)
git push
```

## 3. 스토리 하나 끝날때 체크리스트

- [ ] develop 최신을 내 브랜치에 합쳤다 (`git merge develop`)
- [ ] `./gradlew build`가 내 컴퓨터에서 성공한다
- [ ] 서버를 켜서 **내 스토리의 Talend 테스트**를 다시 돌려 통과했다
- [ ] 내가 만들지 않은 파일이 바뀌지 않았다 (`git diff develop --stat`로 확인)
- [ ] `application-local.yml`, `.env`, 비밀번호가 들어 있지 않다
- [ ] 팀 채팅방에 "ED-13 완료했다" 한 줄 남겼다

## 4. 커밋 메시지

### 4.1 커밋 주기

**기준: "이 커밋이 뭘 했는지 한 문장으로 말할 수 있으면" 커밋한다.**

스토리 하나를 보통 **3~6개 커밋**으로 나눈다.

| 이럴 때 커밋한다                                                     | 이럴 때는 아직 커밋하지 않는다                                        |
| -------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Repository 메서드, DTO, Service, Controller 중 하나를 다 만들었을 때 | 반쯤 짜서 컴파일이 안 될 때 (특히 CRUD, CRUD는 컴파일되고나서)        |
| 버그 하나를 고쳤을 때                                                | 이것저것 고치다 무엇을 바꿨는지 설명이 안 될 때 (→ 나눠서 커밋)       |
| 샘플 데이터 SQL, 설정 파일을 추가했을 때                             | 디버깅용 `System.out.println`, 주석 처리한 코드 덩어리가 남아 있을 때 |

**너무 뜸하다는 신호**

- 2시간 넘게 커밋이 없다 → 너무 큰 덩어리로 작업하고 있다. 끝난 부분까지 먼저 커밋한다.
- 커밋 메시지에 "그리고"가 들어간다 → 두 커밋으로 나눈다.

**커밋 전 확인**

```bash
./gradlew compileJava      # 컴파일되는지 (빠름)
git status                 # 내가 바꾸려던 파일만 있는지
git diff                   # 디버깅 코드가 남아 있지 않은지
```

### 4.2 형식

```
<type>(<scope>): <제목> (<Jira 키>)
```

예:

```
feat(inbound): 입고 문서 목록 조회 API (ED-13)
```

| 부분    | 규칙                                             |
| ------- | ------------------------------------------------ |
| type    | 아래 4.2 중 하나. 소문자                         |
| scope   | 아래 4.3 목록 중 하나. 여러 도메인이면 생략 가능 |
| 제목    | 한글 가능. **50자 이내**, 끝에 마침표 없음       |
| Jira 키 | `(ED-숫자)`. 스토리 작업이면 반드시 붙인다       |

### 4.3 type

| type       | 언제                                        |
| ---------- | ------------------------------------------- |
| `feat`     | 기능 추가                                   |
| `fix`      | 버그 수정                                   |
| `refactor` | 동작은 그대로, 구조만 개선                  |
| `perf`     | 성능 개선. 수치가 있으면 제목에 넣는다      |
| `test`     | 테스트 추가·수정                            |
| `docs`     | 문서 (README, ADR, 결정 로그, 트러블슈팅)   |
| `chore`    | 설정, 빌드, 의존성, 샘플·더미 데이터 SQL    |
| `merge`    | **develop에 병합할 때만** (2.4의 병합 커밋) |

### 4.4 scope

| scope      | 도메인                               | 주로 쓰는 브랜치      |
| ---------- | ------------------------------------ | --------------------- |
| `global`   | 공통 설정, 공통 응답·에러            | `feature/core`        |
| `document` | 입출고 문서 등록                     | `feature/document`    |
| `inbound`  | 입고 목록·상세, 검수, 적재           | `feature/inbound`     |
| `stock`    | 재고 조회                            | `feature/inbound`     |
| `outbound` | 출고 목록·상세, 할당, 피킹, 출고확정 | `feature/outbound`    |
| `product`  | 품목                                 | `feature/master-data` |
| `partner`  | 거래처                               | `feature/master-data` |
| `location` | 칸(로케이션)                         | `feature/master-data` |
| `portal`   | 화주 포털 (나중에)                   | `feature/portal`      |

새 scope가 필요하면 팀장한테 말해준다.(git hook과 CI의 검사 목록때문에)

### 4.5 좋은 예 / 나쁜 예

```
feat(inbound): 검수 등록 API (ED-15)
feat(product): 품목 목록 조회 API (ED-20)
fix(stock): 적재 시 같은 LOT·칸 재고가 두 줄로 생기던 문제 수정 (ED-17)
chore: 입고 흐름 샘플 데이터 SQL 추가 (ED-10)
merge(inbound): 검수 등록 (ED-15)
```

| 나쁜 예                         | 왜                                                   | 고친 예                                                          |
| ------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| `수정`, `wip`, `ㅇㅇ`           | 무엇을? PR이 없어서 **develop 기록에 그대로 남는다** | `fix(inbound): 검수 수량이 합계에 안 들어가던 문제 수정 (ED-15)` |
| `Feat(Inbound): 검수`           | 대문자                                               | `feat(inbound): 검수 등록 API (ED-15)`                           |
| `feat(inbound): 검수 등록 API.` | 마침표                                               | 마침표 삭제                                                      |
| `feat(wms): 입고 기능 완성`     | 없는 scope, 너무 큼                                  | 스토리별로 나눠서 커밋                                           |

### 4.6 커밋 크기

- 커밋 하나 = 한 문장으로 설명되는 변화 하나. "그리고"가 들어가면 두 커밋이다.
- PR이 없어서 **모든 커밋이 develop에 그대로 남는다.** 임시 저장용 커밋(`wip`, `임시`)을 만들지 않는다.

### 4.7 하지 말 것

- `application-local.yml`, `.env`, DB 비밀번호 커밋
- `git add .` 후 확인 없이 커밋
- develop, main에 `--force` 푸시 (자기 feature 브랜치에서만 예외적으로 허용)
- develop에 직접 커밋

## 5. 자동 검사 (git hook + CI) 5번부턴 읽지 않아도 된다.

### 5.1 무엇을 검사하나

| 검사             | 어디서               | 언제                                | 통과 조건                                                                         |
| ---------------- | -------------------- | ----------------------------------- | --------------------------------------------------------------------------------- |
| 커밋 메시지 형식 | git hook (내 컴퓨터) | `git commit` 할 때                  | 6.2 정규식에 맞음. 틀리면 커밋이 안 됨                                            |
| 커밋 메시지 형식 | CI                   | 모든 브랜치 푸시                    | 푸시한 커밋이 전부 6.2에 맞음 (hook을 안 켠 사람 대비)                            |
| 브랜치 이름      | CI                   | 모든 브랜치 푸시                    | `main`, `develop`, `feature/{소문자-하이픈}`, `reference/{소문자-하이픈}` 중 하나 |
| 빌드 + 테스트    | CI                   | `feature/*`, `develop`, `main` 푸시 | `./gradlew build` 성공                                                            |

### 5.2 커밋 메시지 정규식

```
^(feat|fix|refactor|perf|test|docs|chore|merge|release)(\((global|document|inbound|stock|outbound|product|partner|location|portal)\))?: .{1,50}( \(ED-[0-9]+\))?$
```

| 부분                | 뜻                                 |
| ------------------- | ---------------------------------- | ------------ | -------------------------------------------------------------- |
| `(feat              | …                                  | release)`    | type 중 하나 (`merge`는 develop 병합, `release`는 main 배포용) |
| `(\((global         | …                                  | portal)\))?` | scope 목록 중 하나. 생략 가능                                  |
| `: .{1,50}`         | 콜론 + 띄어쓰기 + 제목 1~50자      |
| `( \(ED-[0-9]+\))?` | Jira 키. 생략 가능 (docs·chore 등) |

- git이 자동으로 만드는 `Merge branch 'develop' into feature/inbound` 메시지(2.2 매일 아침 병합)는 **검사에서 제외**한다.

### 5.3 GitHub 저장소 설정 (팀장, 한 번만)

`Settings → Branches → Add branch ruleset`

| 브랜치    | 설정                                                |
| --------- | --------------------------------------------------- |
| `main`    | 팀장만 푸시 가능, force push 금지, 삭제 금지        |
| `develop` | 팀원 전원 푸시 가능, **force push 금지, 삭제 금지** |
