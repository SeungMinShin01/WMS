## 핵심 결과

- 락이 없는 상태에서 같은 자원에 20건을 동시에 요청한 결과, **세 시나리오 모두 3회 중 3회 정합성이 깨졌다.**
- 적재는 실물 80개가 **800개로 기록**되었고(+720), 할당은 **60개가 유실**되면서 17건이 **데드락으로 500**을 반환했다. 출고확정은 **10번 중복 처리**되었다.
- 같은 조건에서 1건만 요청한 대조군은 세 시나리오 모두 정상이었다. **규칙 자체는 올바르며, 동시 요청에서만 깨진다.**
- 동시에 뚫린 건수는 **DB 연결 풀 크기(10)와 일치**한다. 경쟁 조건의 피해 범위가 동시에 실행되는 트랜잭션 수로 결정된다.

## 3. Before 결과

### alloc

| 지표                | 대조군 (VU 1) | 1회        | 2회        | 3회        | 기대값     |
| ------------------- | ------------- | ---------- | ---------- | ---------- | ---------- |
| ok / 409 / 5xx      | 1 / 0 / 0     | 2 / 1 / 17 | 2 / 1 / 17 | 2 / 1 / 17 | 1 / 19 / 0 |
| detail 줄 수 / 합계 | 2 / 60        | 4 / 120    | 4 / 120    | 4 / 120    | 2 / 60     |
| 재고 12·3 선점      | 50 · 50       | 50 · 50    | 50 · 50    | 50 · 50    | 50 · 50    |
| **유실 수량**       | 0             | **60**     | **60**     | **60**     | 0          |
| 문서 14             | PICKING       | PICKING    | PICKING    | PICKING    | PICKING    |
| p95 (ms)            | 56            | 189        | 165        | 151        | —          |

- 유실 수량 = detail 합계 − 선점 증가분
  - 선점 증가분 = 재고 12 (50 − 0) + 재고 3 (50 − 40) = 60
  - 동시 요청: 120 − 60 = **60**
- 두 요청이 모두 성공하여 할당이 두 번 기록되었으나, 재고 선점은 한 번만 반영되었다. 두 요청이 같은 선점값(0, 40)을 읽고 계산 결과를 덮어썼기 때문이다(갱신 유실).
- 5xx 원인은 **데드락**이다 (원본 `deadlock_alloc.txt`, 3회차).
  - 트랜잭션 A: detail INSERT 시 외래키 검사로 재고 3·12에 S 잠금을 보유한 상태에서, 문서 14의 X 잠금을 대기
  - 트랜잭션 B: 문서 14의 X 잠금을 보유한 상태에서, 재고 12의 X 잠금을 대기
  - 잠금 순서가 엇갈린 원형 대기가 발생하여 MySQL이 한쪽을 롤백했다.

| LOT 2 재고 줄 수 / 합계 | 1 / 80        | **10 / 800** | **10 / 800** | **10 / 800** | 1 / 80     |

- 실물 80개가 재고 800개로 기록되었다(+720). 10줄 중 9줄은 어떤 검수 기록에도 연결되지 않은 재고이다.
- "이미 적재됨" 검사를 10건이 동시에 통과하고, 각자 "같은 LOT 재고 없음"으로 판단하여 새 재고 줄을 생성했다.
- 회차마다 검수 기록에 연결된 재고 번호가 다르다(22, 23, 22). 매 회차 실제로 새 재고 줄이 생성되었음을 보여준다.

- 출고 처리가 10번 실행되었으나 최종 재고는 기대값과 같다. 10건이 모두 같은 시작값(60/40, 50/20)을 읽고 같은 결과(20/0, 30/0)를 덮어썼기 때문이다. **갱신 유실이 이중 차감을 가린 상태**이다.

## 5. 분석

- **동시 요청에서만 깨진다**: 대조군(VU 1)은 세 시나리오 모두 성공 1건, 데이터 정상이었다. 검사 규칙은 올바르며, 문제는 여러 트랜잭션이 동시에 같은 상태를 읽는 데서 발생한다.
- **동시에 뚫린 건수가 10건인 이유**: carry·ship은 매 회차 정확히 성공 10, 409 10이었다. 동시에 실행되는 트랜잭션 수가 연결 풀 크기(10)로 제한되기 때문이다. 먼저 연결을 획득한 10건은 같은 상태를 읽어 모두 검사를 통과했고, 나머지 10건은 앞선 트랜잭션의 커밋 이후에 실행되어 정상적으로 거부되었다.
- **3회 결과가 동일한 이유**: 매 회차 시작 상태와 요청이 같고, 20건의 도착 간격(수 ms)이 검사부터 커밋까지 걸리는 시간(수십~수백 ms)보다 훨씬 짧다. 경쟁을 최대로 만든 조건이므로 같은 결과가 매번 재현된다.
- **공통 원인**: 세 시나리오 모두 "검사(읽기) → 쓰기" 사이에 다른 트랜잭션이 끼어들 수 있다. 또한 읽은 값으로 계산한 결과를 덮어쓰는 방식이어서 갱신 유실이 함께 발생한다.
- **alloc만 데드락이 발생한 이유**: 한 요청 안에서 재고(외래키 S 잠금 → UPDATE X 잠금)와 문서(상태 UPDATE X 잠금)를 함께 잠그며, 요청마다 잠금 획득 순서가 일정하지 않다.
- **응답 시간**: 동시 요청의 p95(139~338ms)는 대조군(51~56ms)의 약 3~6배이다. 연결 풀 대기와 잠금 대기가 반영된 값이다.

## 6. 한계

- capacity 초과와 같은 품목 중복 검수는 측정하지 않았다. 태그 시점에는 해당 검사 로직이 없어 순차 요청으로도 초과·중복이 발생하므로, 동시성 문제와 구분할 수 없다. 규칙 추가 후 별도로 측정한다.
- 단일 서버·단일 PC 환경이며, 서버·DB·k6가 같은 머신에서 실행되었다.
- After는 V4 이후 코드(화주, detail 상태 포함)를 대상으로 하므로 스키마 차이가 있다.
- 측정 중 `host.docker.internal` 연결 타임아웃이 간헐적으로 발생했다. 연결 실패(neterr)가 있는 회차는 재측정했으며, 최종 결과는 모두 neterr 0이다.
